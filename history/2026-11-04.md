## 📝 [2026-11-04 10:55] - Completed Task: Hotfix for Production Login 500 Error (Foreign Key Constraint on SQLite Batch Migration & Alembic Sync)

### 📌 Overview
- **Task Code:** HOTFIX-PROD-MIGRATION-FK
- **Description:** Resolved production "Internal Server Error" on the login screen of Sorour Logistics v2.5.0 caused by failed Alembic schema migration on startup (customs_consultation_sessions batch alter failing with sqlite3.IntegrityError: FOREIGN KEY constraint failed), which blocked subsequent migrations (including users.token_version), leaving the app stuck in maintenance mode.

### 📁 Files Changed
- `database/migration_runner.py` — Modified: Disabled `PRAGMA foreign_keys` during `_run_alembic()` for SQLite connections and re-enabled in a `finally` block to allow Alembic `batch_alter_table` table recreation without foreign key violation.
- Production Database (`C:\Users\Hp\AppData\Local\Programs\Sorour Logistics\sorour_logistics.db`) — Fixed: Upgraded safely through migration chain with FK OFF, added `users.token_version`, and synced `alembic_version` to binary head `ee55aa66bb77`.

### 📊 Technical Changes
- **Root Cause 1:** SQLite enforces foreign keys per-connection. When Alembic runs `batch_alter_table` on tables referenced by foreign keys (such as `customs_consultation_sessions`), SQLite drops the old table, triggering `sqlite3.IntegrityError: FOREIGN KEY constraint failed`.
- **Root Cause 2:** The failure halted the migration runner before revision `c9d0e1f2a3b4`, causing user authentication to crash with `no such column: users.token_version`.
- **Code Fix:** Patched `database/migration_runner.py` so that `conn.exec_driver_sql("PRAGMA foreign_keys = OFF;")` runs prior to Alembic migrations on SQLite and restores `ON` in `finally`.
- **Production DB Repair:** Cleaned up orphaned temporary table `_alembic_tmp_customs_consultation_sessions`, completed schema migrations, and synchronized `alembic_version` with installed binary head.
